# Internal organization and structure commands

October 23, 2026. `access/commands.ts` implements organization creation/settings
and program/location creation, rename and archive against local Workers/D1.
These services remain disconnected from the public Worker. No hosted identity
migration, live organization onboarding or policy approval is implied.

## Authority and atomic creation

`createOrganization(CommandContext, CreateOrganizationInput)` requires a live,
verified account with passkey assurance. Principal fields supplied by a caller
cannot upgrade the stored session. An organization-bound federated session cannot
create another organization. Global identity sessions may create after local
passkey verification; their original authentication provenance is retained.

One guarded D1 batch creates the organization, trigger-backed owner/admin
membership, nine ordinary organization-level grants, initial program/location,
proposed baseline policy, audit and command receipt. Reserved administrator and
ownership actions remain derived from current ownership, regardless of grants.
The SQL guard and unique immutable creating-account constraint enforce one
organization per creator, including competing requests with different keys.
Ownership transfer never replenishes that allowance. Organization deletion is
blocked until a separate retention workflow exists.

The recorded defaults are `staff_reviewed` assignment, no eligibility bypass and
no automatic service-hour approval, with status `proposed`. They are planning
records for later review, not an implemented volunteer policy engine or approval
of these product defaults. Creation makes no nonprofit/payment verification claim.

## Commands, scope and versions

| Service | Input and behavior |
| --- | --- |
| `createOrganization` | Bounded name/contact email/IANA time zone, first program and first location. Returns organization identity/settings/version only. |
| `updateOrganization` | Organization ID, complete settings and expected version. Uses `organization.update`; never changes owner, creating account, SSO requirements or policies. |
| `saveProgram` / `saveLocation` | Organization ID and name; omit both ID/version to create, or provide both to update. Optional `archived: true` retains the row and references, hides it from ordinary reads and prevents subsequent edits. |
| `getLocation` / `listLocations` | Tenant-qualified live reads; optional program context matches complete grant intersections. Lists are ordered and bounded to 100, as with programs. |

Administrative writes require stored passkey assurance. Coordinators need an
explicit program/location manage grant; an organization-level manage grant is
required to create a new shared definition. A program/location intersection cannot
authorize changing a definition shared beyond that intersection. A selected
organization supplies no authority. Foreign tenant resources remain inaccessible.

Every mutation rechecks account/session, federation, membership, current grants,
scope, resource state and expected version inside the final atomic batch. A stale
version fails with conflict and creates no successful audit/receipt. Failed audit,
policy, membership, structure or receipt insertion rolls back the whole batch.
The earlier internal `renameProgram` primitive is replaced by `saveProgram`;
the foundation authorization tests now exercise that receipt-backed command too.

## Retry contract

The command key is 16–128 ASCII letters, digits, underscores or hyphens. Receipts
are unique by actor, command, organization scope and key. Creation uses the empty
scope because its organization ID is generated by the server. Different commands
or actors do not share a receipt.

The service derives SHA-256 from a versioned canonical representation of validated
input. `CommandContext.requestDigest` is not trusted as proof of identical input.
Names are trimmed, email lowercased and time-zone aliases resolved before hashing.
Same key/semantic input returns the original safe result; changed input conflicts.
Two same-key requests that miss the initial lookup still commit only once: the
loser rereads the winning receipt after fresh authorization.

Receipts are immutable and retained without an expiry in this initial contract.
A replay rechecks live SQL authority, not cached principal fields. Revoking
membership/grants, disabling a credential/identity/account, expiring a session or
changing required SSO can prevent replay. Replaying an archived structure command
may inspect that retained row for scope matching; this exception never authorizes
a new write or bypasses grant/tenant/session checks. Contact email in a receipt is
ordinary organization contact data; no credentials or confidential narratives are
stored there.

## Migration and verification boundary

`0009_organization_commands.sql` adds nullable contact email for existing rows,
proposed policy and immutable receipt tables, retention/identity guards, indexes
and new append-only audit actions. Existing organizations receive no invented
contact or policy approval. A populated local upgrade preserves old sessions and
audit records and their append-only protection.

Local tests cover complete creation, same-key and creator-limit races, changed
content with a forged request digest, missing owner membership, multi-row rollback,
real signed passkey enrollment, organization-bound SAML denial, retained creator
allowance, foreign tenant IDs, scoped/intersection access, archives, stale-version
races, receipt isolation/revocation and authority changed immediately before commit.
No hosted D1 concurrency, provider acceptance or product UI is claimed.

Recovery, invitations/delegation, membership changes/ownership transfer, SAML
protocol verification, native sign-in and shared UI remain open. Recovery and
ownership transfer must be accepted before live organizations are enabled. Public
API composition still needs HTTP schema validation, CSRF/transport admission and
appropriate abuse controls. Migrations are applied only through a separately
authorized, environment-checked rollout with recovery evidence; delivery never
applies identity migrations automatically.
